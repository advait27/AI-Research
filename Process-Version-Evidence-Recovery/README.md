## Description

This paper investigates how AI-assisted Six Sigma systems can recover evidence-supported improvement decisions when diagnostics fail or corrective actions change the manufacturing process. The framework tracks process and observation versions separately and binds confirmation evidence to the configuration named in a claim. Evidence obtained after a physical repair cannot automatically validate an earlier process version.

Study I separates substantive benefit from prerequisite support in an idealized simulation. Study II evaluates noisy diagnostics, imperfect repairs, eight policies, and three resource budgets, producing 2,880 episodes per policy and 23,040 evaluation traces. Full revalidation produces 92 supported beneficial acceptances at mean cost 16.07; a conservative decision-loss policy produces 34 at mean cost 4.40. Lower expenditure accompanies fewer useful recoveries. A deliberately faulty bookkeeping ablation preserves identical deployment outcomes but produces 92 wrong-version endorsements.

The contribution is a reproducible distinction between actual improvement, evidence admissibility, and claim identity within DMAIC workflows. These are simulation results; no LLM, real manufacturing deployment, or general first-ever novelty is established.

## Reproduce

Use Python 3.10 or later. The experiment and tests use only the Python standard library. Run from this folder:

```sh
python3 -m unittest discover -s tests -v
python3 src/experiment.py
python3 src/experiment.py --n 400 --budget 60 --out results/sensitivity_n400
python3 src/experiment.py --n 1600 --budget 60 --out results/sensitivity_n1600
python3 src/versioned_recovery.py --split development
python3 src/versioned_recovery.py --split evaluation
python3 src/audit_versioned.py
```

These commands regenerate the corresponding results in place. Original defaults use seed 20261027; extension development and evaluation use seeds 20261031 and 20271031. The final extension protocol records all budgets and repetitions; its SHA-256 is included in the evaluation summary. The saved development summary records the earlier v1 protocol hash. Re-running development with the current driver uses the final protocol and includes the added full-revalidation ablation; exact reconstruction of the original development run requires using the retained v1 protocol as `research/VERSIONED_PROTOCOL.json` in a separate working copy. The supplied `results/claim-support-audit.json` is a post-hoc reconstruction and is not regenerated by the experiment drivers.

Evaluation results are in `results/versioned-recovery/evaluation/`: `summary.json`, `trials.csv`, `traces.jsonl`, and `audit.json`. Reference replay checks 23,040 traces with no scoring mismatches.

## Interpretation and limitations

The extension protocol was fixed locally after development. A documented pre-evaluation amendment added a full-revalidation bookkeeping ablation because development showed the decision-loss policy's accepted paths did not exercise calibration. This is not external preregistration. The held-out evaluation retained that negative mechanism-coverage result.

Budgets and costs are abstract units. Priors and diagnostic likelihoods match the simulator; planning utilities and horizons are modeling assumptions. The historical-confounding flag is inactive after randomization, so paired settings differing only in that flag duplicate the recovery task. Exploratory bootstrap intervals use 120 base seed/effect clusters, rather than treating all 2,880 episodes as independent.

The no-version policies deliberately remove bookkeeping checks; they are controlled software ablations, not strong competing planners or evidence of errors by untested LLMs. The reference replay shares the Wilson helper and repair random streams with the generator, so it validates trace consistency rather than independent statistical coverage. Zero observed unsupported acceptances is not an industrial reliability guarantee.
